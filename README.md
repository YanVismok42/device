# Система управления прескриптами

Веб-система для управления персональными лобби участников с публикацией прескриптов в реальном времени, анимацией появления текста в стиле [референса](https://kritzkingvoid.github.io/Prescripts/), и полной изоляцией доступа.

## Возможности

### Главный (Администратор)

- **Сводная таблица**: все участники, статусы, превью прескриптов в одном месте
- **Управление участниками**: создание, удаление, генерация персональной ссылки доступа
- **Редактор прескриптов**: с поддержкой форматирования (жирный, курсив, ссылки, списки)
- **Черновик + публикация**: черновики сохраняются отдельно, публикация мгновенно отправляет прескрипт участнику
- **История версий**: до 50 прошлых версий для каждого прескрипта
- **Шаблоны**: сохранение и переиспользование часто используемых прескриптов
- **Реалтайм**: WebSocket обновления статусов от участников

### Участник

- **Персональное лобби**: изолированный доступ строго к своему прескрипту
- **Scramble-reveal анимация**: текст появляется с эффектом как на референсе — случайные символы → прогрессивное раскрытие, со звуком
- **Форматированный текст**: поддержка HTML-разметки (жирный, курсив, ссылки)
- **Кнопки обратной связи**: «Ознакомлен» / «Выполнено» отправляют статус Главному
- **Индикатор соединения**: показывает статус WebSocket-подключения

## Архитектура

- **Хостинг**: Cloudflare Workers — сервер не засыпает и не имеет холодного старта
- **Backend**: Worker + Durable Object `Hub`. Экземпляр один на всё приложение (`getByName('main')`), поэтому презенс и данные всегда согласованы
- **Storage**: SQLite внутри Durable Object (`ctx.storage.sql`) — переживает деплой и перезапуск
- **WebSocket**: Hibernation API (`ctx.acceptWebSocket`) — пока сообщений нет, объект выгружается из памяти, а соединения остаются живыми
- **Auth**: PBKDF2-хеши паролей (WebCrypto, 100 000 итераций SHA-256), HTTP-only cookies для сессий (раздельные для админа и участников); сессии лежат в базе, поэтому вход переживает перезапуск
- **XSS-защита**: санитайзер HTML в `server/sanitize.js` — оставляет только безопасные теги форматирования
- **Изоляция**: у каждого участника свой уникальный токен; токен участника A не даёт доступ к лобби B

## Установка и запуск

### Требования

- Node.js 18+ (проверено на 24.18.0)
- npm 9+
- Аккаунт Cloudflare (бесплатный, карта не нужна) — для публикации

### Локальный запуск

```bash
git clone https://github.com/YanVismok42/device.git
cd device
npm install
npm run dev
```

Сервер поднимется на **http://localhost:3000** (эмулятор Workers из wrangler).

Логин и пароль для локального запуска берутся из файла `.dev.vars` в корне (в репозиторий он не идёт):

```
ADMIN_USERNAME=admin
ADMIN_PASSWORD=свой-локальный-пароль
```

Локальная база лежит в `.wrangler/` — чтобы начать с нуля, удалите эту папку.

### Публикация на Cloudflare

```bash
npx wrangler login
npm run deploy
npx wrangler secret put ADMIN_PASSWORD
npm run deploy
```

- `wrangler login` откроет браузер и привяжет проект к вашему аккаунту
- при первом деплое спросят имя поддомена — это часть адреса `https://<поддомен>.workers.dev`. Задаётся на весь аккаунт один раз; сменить потом можно в дашборде, но старый адрес сразу умрёт вместе с разосланными ссылками на лобби
- `secret put ADMIN_PASSWORD` спросит пароль Главного (`Enter a secret value:`) — он хранится на стороне Cloudflare, не в коде. Имя секрета уже задано аргументом: если запустить команду без него, wrangler спросит имя, и введённый пароль станет именем секрета — а имена не скрываются и видны в дашборде
- **второй `deploy` обязателен**, если приложение уже открывали до задания секрета. Durable Object создаётся при первом обращении и живёт с тем набором переменных, который был на тот момент; пока его не перезапустить, нового секрета он не увидит и вход будет отвечать `503`
- после деплоя wrangler напечатает адрес вида `device.ВАШ-ПОДДОМЕН.workers.dev`. Сертификат для только что созданного поддомена выписывается не мгновенно — первую минуту возможна ошибка TLS

Логин Главного по умолчанию — `admin`. Чтобы задать другой, добавьте в `wrangler.jsonc`:

```jsonc
"vars": { "ADMIN_USERNAME": "нужный-логин" }
```

### Первый вход

1. Откройте адрес приложения
2. Введите логин (`admin`, если не меняли) и пароль из `ADMIN_PASSWORD`
3. Запись администратора создаётся при первом обращении к приложению. Если вход отвечает `503 Admin is not configured`, значит Durable Object поднялся без секрета — проверьте `npx wrangler secret list` и передеплойте. Пароля по умолчанию в коде нет
4. Смена пароля на уже созданной базе: повторный `secret put` запись админа не перезапишет. Понадобится либо удалить Durable Object вместе с участниками, либо добавить отдельную ручку смены пароля

## Использование

### Создание участника

1. В панели Главного нажмите **+ Новый участник**
2. Укажите **логин** (username, уникальный) и **никнейм** (отображаемое имя)
3. Система создаёт участника и его персональное лобби
4. Скопируйте **ссылку доступа** — она выглядит как `/lobby/ТОКЕН`
5. Отправьте эту ссылку участнику (через мессенджер, email и т.д.)

### Публикация прескрипта

1. Кликните на строку участника в таблице → откроется модальное окно редактора
2. Напишите прескрипт в текстовом поле (поддерживается HTML: `<strong>`, `<em>`, `<p>`, `<a>`, `<ul>`, `<li>` и т.д.)
3. **Сохранить черновик** — сохраняет локально, участник не видит
4. **Опубликовать** — прескрипт мгновенно отправляется участнику через WebSocket

### Шаблоны

1. Нажмите **Шаблоны** в шапке
2. Введите название и содержимое
3. **Сохранить шаблон**
4. При редактировании прескрипта кликните на чип шаблона → текст вставится в редактор

### История версий

В модальном окне редактора внизу отображается список прошлых версий. Кликните на любую запись → текст восстановится в редактор.

### Доступ участника

1. Участник открывает свою ссылку `/lobby/ТОКЕН`
2. Автоматически подключается к своему лобби через WebSocket
3. Когда Главный публикует прескрипт:
   - Текст появляется с эффектом scramble-reveal (сначала случайные символы, потом прогрессивное раскрытие)
   - Играет звук (WebAudio генерация)
4. После анимации появляются кнопки **Ознакомлен** / **Выполнено**
5. Нажатие кнопки отправляет статус Главному

## API

### Аутентификация

#### `POST /api/admin/login`

Вход администратора.

**Body:**
```json
{
  "username": "admin",
  "password": "ваш-пароль"
}
```

**Response 200:**
```json
{ "success": true }
```

**Cookie:** `admin_session` (HttpOnly, 7 дней)

---

### Администрирование (требуется `admin_session`)

#### `GET /api/admin/overview`

Список всех участников с их лобби и прескриптами.

**Response 200:**
```json
[
  {
    "userId": "...",
    "accessToken": "...",
    "username": "ivan",
    "nickname": "Иван",
    "lobbyId": "...",
    "lobbyName": "Lobby #01 - Иван",
    "status": "active",
    "prescript": "Привет Иван! ...",
    "draft": "<p>Черновик...</p>"
  }
]
```

#### `POST /api/admin/users`

Создать участника.

**Body:**
```json
{
  "username": "ivan",
  "nickname": "Иван"
}
```

**Response 201:**
```json
{
  "user": { "id": "...", "accessToken": "...", ... },
  "lobby": { "id": "...", "name": "...", ... },
  "accessUrl": "/lobby/TOKEN"
}
```

#### `DELETE /api/admin/users/:userId`

Удалить участника и его лобби.

**Response 200:**
```json
{ "success": true }
```

#### `PUT /api/admin/lobbies/:lobbyId`

Обновить черновик или имя лобби.

**Body:**
```json
{
  "draft": "<p>Новый текст...</p>",
  "name": "Lobby - Новое имя"
}
```

#### `POST /api/admin/lobbies/:lobbyId/publish`

Опубликовать прескрипт (прошлая версия уходит в историю).

**Body:**
```json
{
  "content": "<p>Привет <strong>Иван</strong>!</p>"
}
```

**Response 200:**
```json
{ "id": "...", "prescript": { "content": "...", "published": true, "publishedAt": 1786019056211 }, ... }
```

#### `GET /api/admin/lobbies/:lobbyId/history`

История версий прескрипта.

**Response 200:**
```json
[
  { "content": "...", "publishedAt": 1786019000000, "archivedAt": 1786019056211 }
]
```

#### `GET /api/admin/templates`

Список шаблонов.

#### `POST /api/admin/templates`

Создать шаблон.

**Body:**
```json
{
  "name": "Шаблон приветствия",
  "content": "<p>Привет!</p>"
}
```

---

### Лобби участника

#### `POST /api/lobby/access`

Получить доступ к лобби по токену (устанавливает `user_session`).

**Body:**
```json
{
  "token": "661c85107c6e2b45fe1dc3b262ad38b1d63b07382ee9533a"
}
```

**Response 200:**
```json
{
  "user": { "id": "...", "nickname": "Иван" },
  "lobby": { "id": "...", "name": "...", "prescript": "...", "status": "active" }
}
```

**Cookie:** `user_session` (HttpOnly, 30 дней)

#### `POST /api/lobby/status`

Обновить статус участника (требуется `user_session`).

**Body:**
```json
{
  "status": "acknowledged"
}
```

или `"completed"`.

---

### WebSocket

**Endpoint:** `ws://localhost:3000/ws?role=admin` или `/ws?role=lobby`

Роль передаёт клиент, а сервер проверяет только соответствующую куку (`admin_session` для `admin`, `user_session` для `lobby`). Так сделано потому, что у Главного, открывшего лобби для проверки, в браузере лежат обе куки, и по одному их набору не понять, из какой вкладки пришло соединение. Соединение без нужной куки получает `401`.

**Сообщения от сервера:**

#### Админу:
```json
{ "type": "user_created", "user": {...}, "lobby": {...} }
{ "type": "user_deleted", "userId": "..." }
{ "type": "status_changed", "lobbyId": "...", "status": "completed" }
{ "type": "presence_changed", "lobbyId": "...", "online": true }
```

#### Участнику:
```json
{ "type": "prescript_updated", "content": "<p>...</p>" }
```

## Безопасность

### Реализовано

- **Пароли**: PBKDF2-SHA256, 100 000 итераций, 16-байтовая соль; сравнение хешей за постоянное время
- **Сессии**: HttpOnly cookies в базе, раздельные для админа (7 дней) и участников (30 дней)
- **XSS**: санитайзер HTML удаляет `<script>`, `<iframe>`, `javascript:` href и другие опасные конструкции. Черновики чистятся так же, как публикации
- **Изоляция**: токены доступа длиной 24 байта, проверка на уровне API
- **Роль WebSocket**: подтверждается кукой на сервере — подделать её параметром `?role=` нельзя

### Сделано для хостинга

- **Пароль админа** задаётся секретом `ADMIN_PASSWORD` на стороне Cloudflare, в коде не хранится. Пароля по умолчанию нет: без секрета вход отвечает `503`
- **Secure-cookies**: флаг `Secure` выставляется, когда запрос пришёл по HTTPS (на Workers это всегда, кроме локального `wrangler dev`)
- **WebSocket** сам переключается на `wss://` на HTTPS-страницах
- **Данные не теряются**: SQLite Durable Object переживает деплой и перезапуск, в отличие от файловой системы бесплатных Node-хостингов

### Осталось для продакшена

1. **Rate limiting**: защита входа от перебора пароля
2. **CSP**: Content Security Policy header дополнительно к санитайзеру
3. **Смена пароля**: сейчас запись админа создаётся один раз и ручки для смены нет
4. **Бэкапы**: выгрузка базы Durable Object по расписанию

## Технические детали

### Анимация scramble-reveal

Реализована в `public/js/scramble.js`:

1. **Фаза scramble** (0.5 сек): все символы случайны
2. **Фаза reveal** (1.5 сек): символы открываются слева направо
3. Пробелы и переносы строк не скрамблируются
4. Звук: WebAudio генерирует digital glitch (square wave + LFO модуляция частоты)

### Санитайзер HTML

`server/sanitize.js` разбирает HTML и оставляет только:

- Форматирование: `<b>`, `<strong>`, `<i>`, `<em>`, `<u>`, `<s>`
- Структура: `<p>`, `<div>`, `<span>`, `<br>`, `<h1>`, `<h2>`, `<h3>`, `<blockquote>`, `<code>`, `<pre>`
- Списки: `<ul>`, `<ol>`, `<li>`
- Ссылки: `<a href="https://...">` (только `http:` и `https:`, с `target="_blank" rel="noopener noreferrer"`)

Всё остальное удаляется.

### Хранилище

`server/store.js` работает с SQLite внутри Durable Object. Таблицы:

| Таблица | Назначение |
|---|---|
| `admin` | Единственная запись (`CHECK id = 1`): логин и PBKDF2-хеш пароля |
| `users` | Участники: логин, никнейм, токен доступа |
| `lobbies` | Лобби: имя, содержимое прескрипта, черновик, статус |
| `history` | Прошлые версии прескриптов, до 50 на лобби |
| `templates` | Шаблоны прескриптов |
| `sessions` | Активные сессии админа и участников |

Гонок при записи нет по устройству Durable Object: обращения к единственному экземпляру обрабатываются по одному, поэтому очередь записи из прошлой файловой версии больше не нужна.

Наружу `store.js` отдаёт лобби в прежней форме — с вложенным объектом `prescript`, — поэтому фронтенд при переезде на Workers менять не пришлось:

```json
{
  "id": "...",
  "userId": "...",
  "name": "Lobby #01 - Иван",
  "prescript": {
    "content": "<p>...</p>",
    "draft": "",
    "published": true,
    "publishedAt": 1786019056211
  },
  "status": "active",
  "statusAt": 1786019060000,
  "createdAt": 1786018781585
}
```

## Стилистика

- **Цветовая схема**: cyan glow (`#99edff`) на почти-чёрном фоне (`#0a0a0a`)
- **Шрифт**: monospace (Pixel / Consolas / Monaco)
- **Анимации**: text-shadow glow, fade-in, spin для загрузки
- **Статус-бейджи**: цветовое кодирование (pending → yellow, active → green, completed → blue, acknowledged → purple)

## Разработка

### Dev-режим с автоперезагрузкой

```bash
npm run dev
```

Поднимает эмулятор Workers (`wrangler dev`); правки в `server/` и `public/` подхватываются на ходу.

### Лимиты бесплатного тарифа Cloudflare

| Ресурс | Лимит |
|---|---|
| Запросы к Worker | 100 000 в сутки |
| Чтение строк в Durable Object | 5 000 000 в сутки |
| Запись строк | 100 000 в сутки |
| Размер хранилища | 5 ГБ |

Durable Objects на бесплатном тарифе доступны только с SQLite-бэкендом — отсюда `new_sqlite_classes` в миграции `wrangler.jsonc`.

### Полезные команды

```bash
npx wrangler tail
```

Живые логи опубликованного Worker.
